# Deployment guide

The root directory is the deployable Next.js application. The default Vercel presets work with the scripts in `package.json`; no separate API deployment is required.

## 1. Environment variables

Copy `.env.example` to `.env.local` for local development. Never commit real credentials.

| Variable | Scope | Required | Purpose |
| --- | --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | Client + server | Yes | Supabase project gateway |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Client + server | Yes | Supabase publishable/anon key; legacy anon name is accepted by helpers |
| `NEXT_PUBLIC_SITE_URL` | Client + server | Yes | Canonical origin for redirects, sitemap, and robots |
| `SUPABASE_SERVICE_ROLE_KEY` | Server only | Yes for admin/moderation | Privileged Supabase operations after role checks |
| `KV_REST_API_URL` / `KV_REST_API_TOKEN` | Server only | Recommended | Vercel Upstash rate-limit namespace |
| `UPSTASH_REDIS_REST_URL` / `UPSTASH_REDIS_REST_TOKEN` | Server only | Alternative | Canonical Upstash names; preferred when both sets are present |
| `CRON_SECRET` | Server only | For scheduled ingestion | Bearer secret for `/api/v1/news/ingest` |
| `STRIPE_SECRET_KEY` | Server only | For billing | Stripe API client |
| `STRIPE_WEBHOOK_SECRET` | Server only | For billing | Verifies webhook signatures |
| `STRIPE_PRICE_MEMBERSHIP_MONTHLY` | Server only | For billing | Recurring platform price id |
| `STRIPE_PLATFORM_FEE_PERCENT` | Server only | Optional | Platform fee, default `10` |

Configuration rules:

- Server-only values must not start with `NEXT_PUBLIC_`.
- Use separate Supabase projects or schemas and separate Upstash namespaces for local, preview, and production.
- Configure Supabase Site URL and redirect allowlist with exact origins before testing auth.
- Configure the Stripe webhook endpoint to `https://<origin>/api/webhooks/stripe` and subscribe to the checkout/completion, subscription lifecycle, account, full-refund, and dispute events handled by `app/api/webhooks/stripe/route.ts`.
- Billing actions return HTTP 503 and hide purchase controls when Stripe variables are missing or still contain `.env.example` placeholders.
- Placeholder detection lives in `lib/env.ts`. Rate limiting falls back to an in-process window when KV is unconfigured or still points at `your-kv.upstash.io`.
- Protected pages fail closed (redirect to `/login`) when Supabase is unconfigured or an auth check fails.

## 2. Preflight checks

Run from the repository root:

```bash
npm install
npm run typecheck
npm run lint
npm test
npm run build
```

Expected baseline at the time of this transformation:

- `typecheck`: pass.
- `lint`: pass with pre-existing warnings in prototype/script files and a small set of existing component warnings.
- `test`: pass.
- `build`: pass; local builds may print the known `@next/swc-darwin-arm64` dlopen/WASM fallback warning without failing.

## 3. Supabase preflight

Run the secret-safe connectivity check first:

```bash
npm run verify:connectivity
```

It prints only masked hosts and configuration shapes, then exits non-zero if the URL or keys are missing, still placeholders, or unreachable.

For an isolated project with the four test accounts and fixtures, run the read-only account/RLS harness:

```bash
npm run verify:integration
```

It requires `PHASE_D_CONFIRM_ISOLATED=yes`, a matching `PHASE_D_PROJECT_REF`, and the `PHASE_D_*` credentials. It refuses the application project and performs no writes. See `docs/phase-d-integration-report.md` for the full isolated-project procedure.

Confirm before release:

1. Auth users, profiles, posts, comments, discussions, replies, follows, reactions, notifications, reports, audit logs, and membership tables are reachable.
2. RLS policies permit user-scoped operations and block cross-user reads/writes.
3. Core social RLS policies and the profile privilege-escalation guard are present in the database, not only in unapplied proposal files.
4. Service-role key is present only in server environment scope.
5. Realtime publication includes `notifications` if realtime updates are expected.
6. Auth redirect URLs include the deployed origin and `/auth/callback`.
7. Email confirmation and password reset templates point at the correct origin.
8. No migration or production data reset is required by this code change.

## 4. Deployment

Use the normal Vercel project flow for the root directory. The build command is `npm run build`; the output is generated by Next.js.

After deployment:

1. Open the public homepage and confirm the white theme at desktop and mobile widths.
2. Register or sign in with a real account.
3. Complete onboarding and confirm profile persistence.
4. Create a short post, snippet, and article.
5. Like, save, comment, follow, and confirm notifications.
6. Create a discussion and a reply.
7. Submit a report as a regular user.
8. Sign in with a moderator account and resolve or remove a report.
9. Sign in with an admin account and change a test user's status or role.
10. If Stripe is configured, test checkout with a Stripe test account and confirm webhook fulfillment.
11. Verify `/api/v1/feed` and a legacy alias such as `/api/feed` return the same payload shape.

## 5. Responsive smoke matrix

Check these widths on the homepage, feed, article, profile, discussion, search, and login flows:

```text
1920  1440  1280  1024  768  390  375
```

For each, verify:

- white body background and `color-scheme: light`;
- no horizontal overflow (`scrollWidth <= clientWidth`);
- navigation and primary actions remain reachable;
- cards and code blocks wrap or scroll without clipping.

## 6. Rollback

If a release fails:

1. Roll back the Vercel deployment to the last known-good build.
2. Do not reset or reseed production data.
3. Revert environment variable changes only after confirming which deployment scope they affect.
4. Re-run the preflight suite against the restored deployment.
5. If a Stripe webhook caused incorrect state, reconcile from the Stripe event ledger rather than granting access from a browser redirect.

## 7. Known external dependencies

| Capability | External requirement |
| --- | --- |
| All persisted data and auth journeys | Reachable Supabase project with correct schema/RLS |
| Rate limiting across instances | Upstash Redis credentials |
| Memberships, payouts, billing portal | Stripe keys, price, webhook endpoint, Connect configuration |
| Scheduled news refresh | `CRON_SECRET` and cron configuration/manual trigger |
| Moderator/admin smoke tests | Provisioned accounts with the corresponding app metadata |
