Docker Networking DevOps

How I finally understood Docker networking without the headaches

Marcus Chen
Published in DevOps Handbook · 6 min read · Oct 14

For years, Docker networking felt like black magic to me. You type docker run -p 8080:80, and somehow your browser connects to Nginx running in an isolated namespace. But the moment you had two containers that needed to talk to each other without exposing ports to 0.0.0.0, everything broke.

Today, let's discard all the abstract RFC specifications and build a clean, physical mental model of how packets actually move between containers, the Linux host bridge, and the outside world.

1. The Virtual Ethernet Pair (veth)

When Docker starts a container with network isolation, Linux creates a pair of connected virtual network interfaces called a veth pair. Think of this like an invisible ethernet cable with two ends:

  • One end sits inside the container's network namespace as eth0.
  • The other end sits in the host network namespace attached to a bridge named docker0.
# Inspect the default bridge on your host
$ ip link show docker0
3: docker0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 qdisc noqueue state UP
    link/ether 02:42:5d:74:e9:1a brd ff:ff:ff:ff:ff:ff
    inet 172.17.0.1/16 brd 172.17.255.255 scope global docker0

2. Why User-Defined Bridges are Mandatory

The default docker0 bridge has one major limitation: it does not support automatic DNS resolution by container name. If container web tries to connect to db:5432, it fails unless you manually link them.

When you create your own custom network with docker network create app-net, Docker spawns an embedded DNS server on 127.0.0.11 inside each container namespace. 

# Create an isolated user-defined bridge
$ docker network create --driver bridge app-network

# Connect two containers effortlessly
$ docker run -d --name redis --network app-network redis:alpine
$ docker run -d --name api --network app-network my-api:latest

# Inside the 'api' container, pinging 'redis' resolves instantly!
$ ping redis
64 bytes from 172.19.0.2: icmp_seq=1 ttl=64 time=0.082 ms

3. Summary Checklist for Production

Whenever you are debugging container connection issues:

  1. Never use the default bridge in production setups. Always create a user-defined network.
  2. Check iptables NAT forwarding rules if external traffic is not routing to mapped ports.
  3. Use docker network inspect <net-name> to verify IP allocations.
